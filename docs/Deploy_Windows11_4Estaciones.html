01

Docker Desktop en Windows 11

WSL2 · Docker Desktop · PostgreSQL en contenedor · Sin máquina virtual
⏱ ~1.5 h
ACTO 1 · EL PORQUÉ

En Windows 11 no existe systemd, ni Nginx de producción, ni el ecosistema de servicios de Linux. La solución profesional es Docker Desktop, que usa WSL2 (un kernel Linux real embebido en Windows) como motor interno. El resultado: los mismos Dockerfile, docker-compose.yml y configuraciones de Nginx de las estaciones 02–04 funcionan sin cambiar una sola línea. Apriendes el mismo flujo que usarás en cualquier servidor de producción.

ACTO 2 · EL CÓMO
1

Docker Desktop incluye WSL2, el motor Docker y Docker Compose. No necesitas instalar nada más. El instalador configura WSL2 automáticamente.

Configurar WSL2 — límite de memoria para tu equipo

Por defecto WSL2 puede usar hasta el 50% de la RAM. Con 16 GB en tu equipo, conviene limitarlo a 6 GB para que Windows y VS Code sigan fluidos mientras Docker corre.

C:\Users\PorrasLuis\.wslconfig 
# Crear o editar el archivo .wslconfig
# (Abrirlo con Notepad directamente desde PowerShell)
notepad "$env:USERPROFILE.wslconfig"

# Contenido del archivo:
[wsl2]
memory=6GB          # máximo RAM para WSL2 (tu equipo tiene 16 GB)
processors=4        # máximo CPUs (tu Ryzen 7 4700U tiene 8 núcleos)
swap=2GB
localhostForwarding=true

# Guardar y cerrar Notepad
# Aplicar los cambios reiniciando WSL2:
wsl --shutdown
# Luego reiniciar Docker Desktop desde la barra de tareas

Comandos esenciales de Docker en PowerShell

# O desde PowerShell: .iniciar-sena.ps1

Write-Host "Iniciando entorno SENA Backend..." -ForegroundColor Cyan

# 1. Arrancar Docker Desktop si no está corriendo
$dockerRunning = Get-Process "Docker Desktop" -ErrorAction SilentlyContinue
if (-not $dockerRunning) {
    Write-Host "Arrancando Docker Desktop..." -ForegroundColor Yellow
    Start-Process "C:Program FilesDockerDockerDocker Desktop.exe"

    # Esperar hasta que el daemon de Docker responda
    Write-Host "Esperando que Docker esté listo..." -ForegroundColor Yellow
    $intentos = 0
    do {
        Start-Sleep -Seconds 3
        $intentos++
        $ok = docker info 2>$null
    } while (-not $ok -and $intentos -lt 20)

    if ($intentos -ge 20) {
        Write-Host "Docker no respondio. Intentalo manualmente." -ForegroundColor Red
        exit 1
    }
}

Write-Host "Docker listo." -ForegroundColor Green

# 2. Ir al proyecto y levantar los contenedores
Set-Location "C:Projectssena_mvc_project"
docker compose up -d

# 3. Mostrar estado
docker compose ps

# 4. Abrir Swagger UI en el navegador
Start-Sleep -Seconds 3
Start-Process "http://localhost/docs"
Write-Host "Backend disponible en http://localhost/docs" -ForegroundColor Green

Docker + Nginx

Dockerfile · docker-compose · Nginx · Volúmenes · Mismos archivos que en Linux
⏱ ~1.5 h
ACTO 1 · EL PORQUÉ

Esta estación es idéntica a la versión Linux. Los archivos Dockerfile, docker-compose.yml y nginx/nginx.conf no cambian ni una línea. La única diferencia es que en Windows el comando docker compose se escribe en PowerShell en vez de en Bash — y funciona igual.

ACTO 2 · EL CÓMO
1

Dockerfile — exactamente igual que en Linux

El Dockerfile no tiene nada de Linux-específico: construye una imagen basada en Python que corre en cualquier plataforma que tenga Docker. No cambiar nada.

Dockerfile 
# Dockerfile — sin cambios respecto a la versión Linux
FROM python:3.12-slim AS builder
WORKDIR /build
RUN pip install --upgrade pip
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /install /usr/local
COPY ./app ./app
RUN adduser --disabled-password --gecos "" appuser &&     chown -R appuser:appuser /app
USER appuser
EXPOSE 8000
CMD ["uvicorn", "app.main:app",
     "--host", "0.0.0.0",
     "--port", "8000",
     "--workers", "2"]

docker-compose.yml — único ajuste: rutas con barras normales

Docker en Windows acepta rutas con barra normal (/) igual que Linux. La única diferencia real es que el volumen de datos de PostgreSQL se almacena en WSL2 internamente — completamente transparente.

docker-compose.yml 
services:

  db:
    image: postgres:16-alpine
    container_name: sena-db
    restart: unless-stopped
    environment:
      POSTGRES_USER:     ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB:       ${DB_NAME}
    volumes:
      # Igual que Linux: Docker gestiona el volumen internamente en WSL2
      - postgres_data:/var/lib/postgresql/data
    networks:
      - sena-net
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER} -d ${DB_NAME}"]
      interval: 10s
      timeout: 5s
      retries: 5

  backend:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: sena-backend
    restart: unless-stopped
    env_file:
      - .env
    environment:
      DB_HOST: db
    depends_on:
      db:
        condition: service_healthy
    networks:
      - sena-net
    expose:
      - "8000"

  nginx:
    image: nginx:alpine
    container_name: sena-nginx
    restart: unless-stopped
    ports:
      - "80:80"
    volumes:
      # Ruta relativa: funciona igual en Windows y Linux
      - ./nginx/nginx.conf:/etc/nginx/conf.d/default.conf:ro
      - ./frontend/dist/sena-frontend/browser:/usr/share/nginx/html:ro
    depends_on:
      - backend
    networks:
      - sena-net

volumes:
  postgres_data:

networks:
  sena-net:
    driver: bridge

nginx/nginx.conf — sin cambios respecto a Linux

La configuración de Nginx corre dentro del contenedor Linux de Nginx, no en Windows. Por eso es idéntica.

nginx/nginx.conf 
upstream backend_api {
    server backend:8000;
}

server {
    listen 80;
    server_name _;

    location /api/ {
        proxy_pass         http://backend_api/;
        proxy_http_version 1.1;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_read_timeout 60s;
    }

    location /docs {
        proxy_pass http://backend_api/docs;
        proxy_set_header Host $host;
    }

    location /openapi.json {
        proxy_pass http://backend_api/openapi.json;
        proxy_set_header Host $host;
    }

    location / {
        root  /usr/share/nginx/html;
        index index.html;
        try_files $uri $uri/ /index.html;
    }
}

Docker + Traefik + SSL automático

Traefik v3 · Let's Encrypt · Labels · Ajuste de permisos en Windows
⏱ ~1.5 h
ACTO 1 · EL PORQUÉ

Traefik en Windows con Docker Desktop funciona igual que en Linux, con un único ajuste crítico: el archivo acme.json que almacena los certificados SSL debe tener permisos 600 en Linux, pero en Windows esos permisos los gestiona el contenedor internamente. Se resuelve con una línea en el docker-compose.yml.

ACTO 2 · EL CÓMO
1

Crear la carpeta traefik y el acme.json en Windows

En Linux hacemos "chmod 600 acme.json" para restringir permisos. En Windows ese comando no existe, pero Docker Desktop gestiona los permisos del archivo internamente a través de WSL2.

PowerShell 
# Crear la carpeta y el archivo (PowerShell)
cd C:Projectssena_mvc_project
mkdir traefik -ErrorAction SilentlyContinue

# Crear el acme.json vacío (los permisos los gestiona Docker internamente)
New-Item -Path traefikacme.json -ItemType File -Force

# En Windows NO es necesario chmod 600
# Docker Desktop lo gestiona a través de WSL2 automáticamente

# Verificar estructura
Get-ChildItem traefik
# acme.json    traefik.yml
2

traefik/traefik.yml — sin cambios respecto a Linux

La configuración de Traefik es idéntica. Corre dentro de su contenedor Linux, no en Windows.

traefik/traefik.yml 
entryPoints:
  web:
    address: ":80"
    http:
      redirections:
        entryPoint:
          to: websecure
          scheme: https
  websecure:
    address: ":443"
    http:
      tls:
        certResolver: letsencrypt

providers:
  docker:
    endpoint: "unix:///var/run/docker.sock"
    exposedByDefault: false
    network: sena-net

certificatesResolvers:
  letsencrypt:
    acme:
      email: tu-email@ejemplo.com
      storage: /acme.json
      httpChallenge:
        entryPoint: web

api:
  dashboard: true
  insecure: true

docker-compose.yml con Traefik — ajuste de permisos en Windows

El único cambio respecto a Linux: agregamos un comando de inicio que establece los permisos del acme.json dentro del contenedor, solucionando el error de "file too open" de Let's Encrypt.

docker-compose.yml 
services:

  traefik:
    image: traefik:v3.0
    container_name: sena-traefik
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
      - "8080:8080"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
      - ./traefik/traefik.yml:/traefik.yml:ro
      - ./traefik/acme.json:/acme.json
    # AJUSTE WINDOWS: fijar permisos del acme.json al arrancar
    # Let's Encrypt rechaza el archivo si tiene permisos muy abiertos
    entrypoint:
      - sh
      - -c
      - "chmod 600 /acme.json && traefik"
    networks:
      - sena-net

  db:
    image: postgres:16-alpine
    container_name: sena-db
    restart: unless-stopped
    environment:
      POSTGRES_USER:     ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB:       ${DB_NAME}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    networks:
      - sena-net
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER} -d ${DB_NAME}"]
      interval: 10s
      retries: 5

  backend:
    build: .
    container_name: sena-backend
    restart: unless-stopped
    env_file: .env
    environment:
      DB_HOST: db
    depends_on:
      db:
        condition: service_healthy
    networks:
      - sena-net
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.backend.rule=Host(`api.tu-dominio.com`)"
      - "traefik.http.routers.backend.entrypoints=websecure"
      - "traefik.http.routers.backend.tls=true"
      - "traefik.http.routers.backend.tls.certresolver=letsencrypt"
      - "traefik.http.services.backend.loadbalancer.server.port=8000"

  frontend:
    image: nginx:alpine
    container_name: sena-frontend
    restart: unless-stopped
    volumes:
      - ./frontend/dist/sena-frontend/browser:/usr/share/nginx/html:ro
    networks:
      - sena-net
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.frontend.rule=Host(`tu-dominio.com`)"
      - "traefik.http.routers.frontend.entrypoints=websecure"
      - "traefik.http.routers.frontend.tls=true"
      - "traefik.http.routers.frontend.tls.certresolver=letsencrypt"
      - "traefik.http.services.frontend.loadbalancer.server.port=80"

volumes:
  postgres_data:

networks:
  sena-net:
    driver: bridge

Lleva el conocimiento más lejos

Traefik en desarrollo local sin dominio real no puede obtener certificado SSL de Let's Encrypt. Crea una configuración alternativa "docker-compose.local.yml" que use HTTP simple (sin SSL) para desarrollo en Windows, de modo que puedas usar "docker compose -f docker-compose.yml -f docker-compose.local.yml up" para sobreescribir solo la parte de Traefik.

📂 Ver solución del reto

▼

docker-compose.local.yml — override para desarrollo local

docker-compose.local.yml 
# docker-compose.local.yml
# Override solo para desarrollo local sin dominio real
# Uso: docker compose -f docker-compose.yml -f docker-compose.local.yml up -d

services:
  traefik:
    # Sobreescribir el comando para usar HTTP simple (sin ACME/Let's Encrypt)
    command:
      - "--api.insecure=true"
      - "--providers.docker=true"
      - "--providers.docker.exposedbydefault=false"
      - "--entrypoints.web.address=:80"
      # Sin entrypoint websecure ni certificatesResolvers
    # No montar el traefik.yml (usamos --command directamente)
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
      # No montar acme.json ni traefik.yml en modo local

  backend:
    labels:
      # Sobreescribir labels: usar HTTP en vez de HTTPS, localhost en vez de dominio
      - "traefik.enable=true"
      - "traefik.http.routers.backend.rule=PathPrefix(`/api`)"
      - "traefik.http.routers.backend.entrypoints=web"
      - "traefik.http.services.backend.loadbalancer.server.port=8000"

  frontend:
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.frontend.rule=PathPrefix(`/`)"
      - "traefik.http.routers.frontend.entrypoints=web"
      - "traefik.http.services.frontend.loadbalancer.server.port=80"

Uso desde PowerShell

PowerShell

# Producción (servidor real con dominio):

GitHub Actions · Docker Hub · SSH al servidor · Mismo pipeline que Linux

ACTO 1 · EL PORQUÉ

El pipeline de CI/CD corre en los servidores de GitHub (Ubuntu), no en tu Windows. Por eso es 100% idéntico a la versión Linux: los jobs de GitHub Actions siempre corren en Linux independientemente de tu sistema operativo local. Tu rol es solo configurar los Secrets y hacer push desde PowerShell.

Generar par de claves SSH para el deploy en Windows

La clave SSH privada se guarda en GitHub Secrets y la pública en el servidor. Se genera en PowerShell con ssh-keygen, que viene incluido en Windows 10/11.

PowerShell 
# Generar par de claves ED25519 (más seguro y más corto que RSA)
ssh-keygen -t ed25519 -C "github-actions-deploy" -f "$env:USERPROFILE.sshgithub_actions_deploy"
# Passphrase: dejar VACÍO (Enter) — el workflow no puede ingresar passphrase

# Ver la clave privada (copiar al Secret SSH_PRIVATE_KEY en GitHub)
Get-Content "$env:USERPROFILE.sshgithub_actions_deploy"
# -----BEGIN OPENSSH PRIVATE KEY-----
# b3BlbnNzaC1rZXktdjEAAAAABG5vbmUAAAA...
# -----END OPENSSH PRIVATE KEY-----

# Ver la clave pública (agregar al servidor)
Get-Content "$env:USERPROFILE.sshgithub_actions_deploy.pub"
# ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA... github-actions-deploy

# Agregar la clave pública al servidor (ejecutar en el servidor Linux):
# echo "ssh-ed25519 AAAAC3Nz..." >> ~/.ssh/authorized_keys

Lleva el conocimiento más lejos

Agrega una notificación por correo cuando el pipeline falle. Usa la action "dawidd6/action-send-mail" para enviar un email con el link al log del job fallido y el mensaje de error.

📂 Ver solución del reto

▼

Agregar el step de notificación al workflow

.github/workflows/deploy.yml 
# Agregar este job al final del workflow (después de "deploy"):

  notify-failure:
    name: Notificar fallo
    # Solo se ejecuta si algún job anterior falló
    needs: [test, build-and-push, deploy]
    if: failure()
    runs-on: ubuntu-latest

    steps:
      - name: Enviar email de notificación
        uses: dawidd6/action-send-mail@v3
        with:
          server_address: smtp.gmail.com
          server_port:    465
          secure:         true
          username:       ${{ secrets.MAIL_USERNAME }}
          password:       ${{ secrets.MAIL_PASSWORD }}
          subject:        "❌ Pipeline fallido — sena_mvc_project"
          to:             lporras567@gmail.com
          from:           GitHub Actions
          body: |
            El pipeline de CI/CD ha fallado.

            Repositorio: ${{ github.repository }}
            Rama:        ${{ github.ref_name }}
            Commit:      ${{ github.sha }}
            Actor:       ${{ github.actor }}

            Ver el log completo:
            https://github.com/${{ github.repository }}/actions/runs/${{ github.run_id }}
