Deploy del Backend FastAPI — 4 Estaciones

Sin Docker · Docker + Nginx · Docker + Traefik + SSL automático · CI/CD con GitHub Actions

01

Deploy sin Docker

Ubuntu 24.04 · PostgreSQL · Uvicorn · Nginx como proxy reverso
⏱ ~2.5 h
ACTO 1 · EL PORQUÉ

En producción real la combinación más frecuente en servidores VPS (DigitalOcean, Hetzner, Linode) es Ubuntu + PostgreSQL nativo + Uvicorn gestionado por systemd + Nginx como proxy reverso. Aprender este flujo sin Docker te da control total sobre el servidor y es la base para entender qué hace Docker por ti.

ACTO 2 · EL CÓMO
1

Actualizar servidor e instalar dependencias del sistema

Partimos de un VPS Ubuntu 24.04 limpio. Instalamos Python, PostgreSQL y Nginx en un solo bloque.

terminal (servidor Ubuntu) 
# Actualizar paquetes
sudo apt update && sudo apt upgrade -y

# Python 3.12, pip, venv y git
sudo apt install -y python3.12 python3.12-venv python3-pip git

# PostgreSQL 16
sudo apt install -y postgresql postgresql-contrib

# Nginx
sudo apt install -y nginx

# Verificar que todo quedó instalado
python3 --version      # Python 3.12.x
psql --version         # psql 16.x
nginx -v               # nginx/1.x

Configurar PostgreSQL — usuario y base de datos

PostgreSQL crea el usuario postgres por defecto. Creamos un usuario dedicado para la aplicación y la base de datos.

terminal (servidor) 
# Iniciar PostgreSQL si no está corriendo
sudo systemctl enable postgresql
sudo systemctl start postgresql

# Ingresar como superusuario de PostgreSQL
sudo -u postgres psql

CREATE USER sena_user WITH PASSWORD 'sena_pass_segura_2026';

\q

# Verificar conexión con el nuevo usuario
psql -U sena_user -d sena_mvc_db -h localhost -c "SELECT 1;"
# Debe responder: ?column? = 1

Clonar el proyecto y configurar el entorno virtual

Clonamos el repositorio en /opt/ (ubicación estándar para aplicaciones de producción en Linux) y creamos el venv.

terminal (servidor) 
# Clonar el repositorio

source venv/bin/activate

# Instalar dependencias

pip install -r requirements.txt

# Verificar que FastAPI arranca

Crear el servicio systemd — Uvicorn como demonio

systemd convierte Uvicorn en un servicio del sistema: arranca automáticamente al iniciar el servidor, se reinicia si falla y guarda logs en journald.

/etc/systemd/system/sena-backend.service 
# Crear el archivo de servicio
sudo nano /etc/systemd/system/sena-backend.service

# Contenido del archivo:
[Unit]
Description=SENA Backend FastAPI - MVC Async
After=network.target postgresql.service
Requires=postgresql.service

[Service]
User=ubuntu
Group=ubuntu
WorkingDirectory=/opt/sena-backend
EnvironmentFile=/opt/sena-backend/.env
ExecStart=/opt/sena-backend/venv/bin/uvicorn app.main:app     --host 127.0.0.1     --port 8000     --workers 2
Restart=always
RestartSec=3
StandardOutput=journal
StandardError=journal

[Install]
WantedBy=multi-user.target

# Activar y arrancar el servicio
sudo systemctl daemon-reload
sudo systemctl enable sena-backend
sudo systemctl start sena-backend

# Verificar que está corriendo
sudo systemctl status sena-backend
# Debe mostrar: Active: active (running)

# Ver los logs en tiempo real
sudo journalctl -u sena-backend -f
6

Configurar Nginx como proxy reverso

Nginx recibe las peticiones en el puerto 80 (o 443 con SSL) y las reenvía a Uvicorn en el puerto 8000 interno. También sirve el frontend Angular desde /dist.

/etc/nginx/sites-available/sena-backend 
# Crear configuración de Nginx
sudo nano /etc/nginx/sites-available/sena-backend

# Contenido:
server {
    listen 80;
    server_name tu-dominio.com www.tu-dominio.com;
    # Para IP directa: server_name _;

    # ── API Backend ──
    location /api/ {
        proxy_pass         http://127.0.0.1:8000/;
        proxy_http_version 1.1;
        proxy_set_header   Upgrade $http_upgrade;
        proxy_set_header   Connection 'upgrade';
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_cache_bypass $http_upgrade;
        proxy_read_timeout 60s;
    }

    # ── Frontend Angular ──
    location / {
        root   /opt/sena-backend/frontend/dist/sena-frontend/browser;
        index  index.html;
        # SPA routing: redirigir todo al index.html
        try_files $uri $uri/ /index.html;
    }
}

# Activar el sitio
sudo ln -s /etc/nginx/sites-available/sena-backend            /etc/nginx/sites-enabled/

# Verificar configuración
sudo nginx -t
# nginx: configuration file ... syntax is ok
# nginx: configuration file ... test is successful

# Recargar Nginx
sudo systemctl reload nginx

SSL con Certbot (HTTPS gratuito)

Certbot de Let's Encrypt genera y renueva automáticamente un certificado SSL gratuito. Solo funciona con dominio real (no con IP).

terminal (servidor) 
# Instalar Certbot para Nginx
sudo apt install -y certbot python3-certbot-nginx

# Obtener certificado (reemplazar con tu dominio real)
sudo certbot --nginx -d tu-dominio.com -d www.tu-dominio.com

# Certbot modifica automáticamente la config de Nginx para HTTPS
# y programa la renovación automática cada 90 días

# Verificar renovación automática
sudo certbot renew --dry-run
# Debe decir: All renewals succeeded

# Ver el certificado instalado
sudo certbot certificates

Lleva el conocimiento más lejos

El servidor está corriendo pero los logs muestran muchas peticiones lentas. Configura Gunicorn como process manager en vez de Uvicorn directamente: instala gunicorn, crea un archivo gunicorn.conf.py con 4 workers y ajusta el ExecStart del servicio systemd para usar gunicorn con el worker class uvicorn.workers.UvicornWorker.

📂 Ver solución del reto

▼

1. Instalar Gunicorn en el venv

terminal 
cd /opt/sena-backend
source venv/bin/activate
pip install gunicorn
pip freeze > requirements.txt

2. Archivo de configuración de Gunicorn

/opt/sena-backend/gunicorn.conf.py 
import multiprocessing

# Número de workers: regla empírica = (2 × CPUs) + 1
workers = multiprocessing.cpu_count() * 2 + 1

# Worker class: Uvicorn para compatibilidad con FastAPI async
worker_class = "uvicorn.workers.UvicornWorker"

# Dirección de escucha (solo localhost, Nginx hace el proxy)
bind = "127.0.0.1:8000"

# Timeouts
timeout  = 60
keepalive = 5

# Logging
accesslog = "/var/log/sena-backend/access.log"
errorlog  = "/var/log/sena-backend/error.log"
loglevel  = "info"

# Reinicio automático al cambiar el código (solo dev)
# reload = True

3. Actualizar el servicio systemd

/etc/systemd/system/sena-backend.service 
[Service]
# Reemplazar la línea ExecStart anterior por:
ExecStart=/opt/sena-backend/venv/bin/gunicorn app.main:app     --config /opt/sena-backend/gunicorn.conf.py

# Crear directorio de logs
sudo mkdir -p /var/log/sena-backend
sudo chown ubuntu:ubuntu /var/log/sena-backend

# Recargar systemd y reiniciar
sudo systemctl daemon-reload
sudo systemctl restart sena-backend
sudo systemctl status sena-backend
02

Docker — Contenedores

Dockerfile · docker-compose · Red de contenedores · Volúmenes para persistencia
⏱ ~2 h
ACTO 1 · EL PORQUÉ

Docker empaqueta la aplicación y todas sus dependencias en un contenedor aislado: el mismo imagen corre igual en tu máquina, en el servidor y en la nube. docker-compose orquesta los tres contenedores (FastAPI, PostgreSQL, Nginx) como si fueran un solo servicio. Esto elimina el "funciona en mi máquina" para siempre.

ACTO 2 · EL CÓMO
1

Instalar Docker y Docker Compose en Ubuntu

Docker oficial se instala desde el repositorio de Docker, no del apt de Ubuntu (que tiene una versión desactualizada).

terminal (servidor o local) 
# Instalar Docker Engine (método oficial)
curl -fsSL https://get.docker.com | sudo bash

# Agregar tu usuario al grupo docker (evitar usar sudo en cada comando)
sudo usermod -aG docker $USER
newgrp docker   # aplicar sin cerrar sesión

# Verificar instalación
docker --version         # Docker version 27.x
docker compose version   # Docker Compose version v2.x

# Prueba rápida
docker run hello-world
2

Dockerfile — imagen del backend

El Dockerfile describe cómo construir la imagen del backend. Usamos Python 3.12-slim (imagen mínima) y una construcción en dos etapas para reducir el tamaño final.

Dockerfile 
# Dockerfile (en la raíz del proyecto sena_mvc_project/)

# ── Etapa 1: instalar dependencias ──
FROM python:3.12-slim AS deps

WORKDIR /app

# Copiar solo requirements primero (caché de Docker)
# Si requirements.txt no cambia, Docker reutiliza esta capa
COPY requirements.txt .
RUN pip install --no-cache-dir --upgrade pip &&     pip install --no-cache-dir -r requirements.txt

# ── Etapa 2: imagen final ──
FROM python:3.12-slim

WORKDIR /app

# Copiar dependencias instaladas desde la etapa anterior
COPY --from=deps /usr/local/lib/python3.12/site-packages                  /usr/local/lib/python3.12/site-packages
COPY --from=deps /usr/local/bin /usr/local/bin

# Copiar el código de la aplicación
COPY ./app ./app

# Usuario no-root por seguridad
RUN adduser --disabled-password --gecos "" appuser
USER appuser

# Puerto que expone el contenedor (documentación)
EXPOSE 8000

# Comando de arranque con Gunicorn + UvicornWorker
CMD ["gunicorn", "app.main:app",      "--worker-class", "uvicorn.workers.UvicornWorker",      "--bind", "0.0.0.0:8000",      "--workers", "2",      "--timeout", "60"]

docker-compose.yml — orquestar los 3 contenedores

Un solo archivo define los tres servicios (backend, db, nginx), la red que los conecta y el volumen para que los datos de PostgreSQL persistan aunque el contenedor se reinicie.

docker-compose.yml 
services:

  # ── Base de datos PostgreSQL ──
  db:
    image: postgres:16-alpine
    container_name: sena-db
    restart: unless-stopped
    environment:
      POSTGRES_USER:     ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB:       ${DB_NAME}
    volumes:
      - postgres_data:/var/lib/postgresql/data
      # Script de inicialización (opcional)
      # - ./database.sql:/docker-entrypoint-initdb.d/init.sql
    networks:
      - sena-net
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER} -d ${DB_NAME}"]
      interval: 10s
      timeout: 5s
      retries: 5

  # ── Backend FastAPI ──
  backend:
    build:
      context: .
      dockerfile: Dockerfile
    container_name: sena-backend
    restart: unless-stopped
    env_file:
      - .env
    environment:
      # En Docker, "db" es el hostname del contenedor PostgreSQL
      DB_HOST: db
    depends_on:
      db:
        condition: service_healthy   # espera que PostgreSQL esté listo
    networks:
      - sena-net
    expose:
      - "8000"   # solo visible dentro de la red Docker, no al exterior

  # ── Nginx ──
  nginx:
    image: nginx:alpine
    container_name: sena-nginx
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/conf.d/default.conf:ro
      # Frontend Angular (build de producción)
      - ./frontend/dist/sena-frontend/browser:/usr/share/nginx/html:ro
      # Certificados SSL (si usas Certbot manual)
      # - /etc/letsencrypt:/etc/letsencrypt:ro
    depends_on:
      - backend
    networks:
      - sena-net

volumes:
  postgres_data:   # volumen nombrado: persiste aunque el contenedor muera

networks:
  sena-net:
    driver: bridge
5

nginx/nginx.conf — configuración para el contenedor

Esta configuración va dentro del contenedor nginx. El servidor upstream se llama "backend" porque ese es el nombre del servicio en docker-compose, no localhost.

nginx/nginx.conf 
# nginx/nginx.conf
upstream backend_api {
    server backend:8000;   # "backend" = nombre del servicio en docker-compose
}

server {
    listen 80;
    server_name _;   # cualquier hostname

    # ── API ──
    location /api/ {
        proxy_pass         http://backend_api/;
        proxy_http_version 1.1;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }

    # ── Swagger UI (acceso directo en desarrollo) ──
    location /docs {
        proxy_pass http://backend_api/docs;
        proxy_set_header Host $host;
    }

    location /openapi.json {
        proxy_pass http://backend_api/openapi.json;
        proxy_set_header Host $host;
    }

    # ── Frontend Angular ──
    location / {
        root  /usr/share/nginx/html;
        index index.html;
        try_files $uri $uri/ /index.html;   # SPA routing
    }
}

Lleva el conocimiento más lejos

La imagen del backend pesa demasiado. Analiza el tamaño con "docker images" y optimiza el Dockerfile usando multi-stage build para que la imagen final no incluya pip ni los archivos de compilación. El objetivo es que la imagen quede por debajo de 200 MB.

📂 Ver solución del reto

▼

1. Ver el tamaño actual de la imagen

Dockerfile

FROM python:3.12-slim AS builder

WORKDIR /build

RUN pip install --upgrade pip
COPY requirements.txt .

RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

# ── Etapa 2: imagen final mínima ──
FROM python:3.12-slim

# Copiar SOLO los paquetes instalados (sin pip, sin compiladores)

# Copiar el código de la aplicación

Docker + SSL automático con Traefik

Traefik como reverse proxy · Let's Encrypt automático · Labels en docker-compose
⏱ ~1.5 h
ACTO 1 · EL PORQUÉ

Nginx requiere configurar SSL manualmente con Certbot. Traefik es un proxy reverso diseñado para contenedores: detecta automáticamente los servicios de Docker mediante labels y gestiona los certificados SSL de Let's Encrypt sin intervención manual. Es el estándar en entornos de producción con Docker.

ACTO 2 · EL CÓMO
1

Estructura de archivos para Traefik

Traefik necesita un archivo de configuración estática y una carpeta para almacenar los certificados SSL. Los certificados se persisten en un volumen para no regenerarlos en cada reinicio.

terminal (raíz del proyecto) 
# Estructura de archivos a crear
mkdir -p traefik
touch traefik/traefik.yml
touch traefik/acme.json
chmod 600 traefik/acme.json   # ← OBLIGATORIO: Let's Encrypt falla si no es 600

# La estructura queda así:
# sena_mvc_project/
# ├── app/
# ├── traefik/
# │   ├── traefik.yml    ← config estática de Traefik
# │   └── acme.json      ← almacén de certificados SSL (vacío al inicio)
# ├── Dockerfile
# ├── docker-compose.yml
# └── .env
2

traefik/traefik.yml — configuración estática

La configuración estática define los puntos de entrada (puertos), el proveedor Docker y el resolutor de certificados. Solo se lee al arrancar Traefik.

traefik/traefik.yml 
# traefik/traefik.yml

# ── Puntos de entrada ──
entryPoints:
  web:
    address: ":80"
    # Redirigir HTTP → HTTPS automáticamente
    http:
      redirections:
        entryPoint:
          to: websecure
          scheme: https

  websecure:
    address: ":443"
    http:
      tls:
        certResolver: letsencrypt

# ── Proveedor: Docker ──
providers:
  docker:
    endpoint: "unix:///var/run/docker.sock"
    exposedByDefault: false   # solo exponer servicios con label enable=true
    network: sena-net

# ── Certificados SSL con Let's Encrypt ──
certificatesResolvers:
  letsencrypt:
    acme:
      email: tu-email@ejemplo.com     # ← cambiar por email real
      storage: /acme.json
      httpChallenge:
        entryPoint: web

# ── Dashboard de Traefik (solo en desarrollo) ──
api:
  dashboard: true
  insecure: true   # quitar en producción
3

docker-compose.yml con Traefik y labels

El secreto de Traefik es la sección "labels": cada servicio le dice a Traefik su hostname, su puerto y su router. No hay que tocar nginx.conf.

docker-compose.yml 
services:

  # ── Traefik ──
  traefik:
    image: traefik:v3.0
    container_name: sena-traefik
    restart: unless-stopped
    ports:
      - "80:80"
      - "443:443"
      - "8080:8080"   # dashboard (quitar en producción)
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
      - ./traefik/traefik.yml:/traefik.yml:ro
      - ./traefik/acme.json:/acme.json
    networks:
      - sena-net

  # ── Base de datos ──
  db:
    image: postgres:16-alpine
    container_name: sena-db
    restart: unless-stopped
    environment:
      POSTGRES_USER:     ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
      POSTGRES_DB:       ${DB_NAME}
    volumes:
      - postgres_data:/var/lib/postgresql/data
    networks:
      - sena-net
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER} -d ${DB_NAME}"]
      interval: 10s
      retries: 5

  # ── Backend FastAPI ──
  backend:
    build: .
    container_name: sena-backend
    restart: unless-stopped
    env_file: .env
    environment:
      DB_HOST: db
    depends_on:
      db:
        condition: service_healthy
    networks:
      - sena-net
    # ← Traefik lee estos labels y configura el routing automáticamente
    labels:
      - "traefik.enable=true"
      # Router para /api
      - "traefik.http.routers.backend.rule=Host(`api.tu-dominio.com`)"
      - "traefik.http.routers.backend.entrypoints=websecure"
      - "traefik.http.routers.backend.tls=true"
      - "traefik.http.routers.backend.tls.certresolver=letsencrypt"
      # Puerto interno del contenedor
      - "traefik.http.services.backend.loadbalancer.server.port=8000"

  # ── Frontend Angular ──
  frontend:
    image: nginx:alpine
    container_name: sena-frontend
    restart: unless-stopped
    volumes:
      - ./frontend/dist/sena-frontend/browser:/usr/share/nginx/html:ro
    networks:
      - sena-net
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.frontend.rule=Host(`tu-dominio.com`)"
      - "traefik.http.routers.frontend.entrypoints=websecure"
      - "traefik.http.routers.frontend.tls=true"
      - "traefik.http.routers.frontend.tls.certresolver=letsencrypt"
      - "traefik.http.services.frontend.loadbalancer.server.port=80"

volumes:
  postgres_data:

networks:
  sena-net:
    driver: bridge

04

CI/CD — Deploy automático

GitHub Actions · SSH deploy · Docker Hub · Variables de entorno en GitHub Secrets
⏱ ~1.5 h
ACTO 1 · EL PORQUÉ

Sin CI/CD cada deploy es un proceso manual propenso a errores: conectarse por SSH, hacer git pull, reiniciar el servicio y rezar para que nada falle. Con GitHub Actions, cada push a la rama main desencadena automáticamente: pruebas → build de la imagen Docker → push a Docker Hub → deploy en el servidor vía SSH. Cero intervención manual.

ACTO 2 · EL CÓMO
1

Crear cuenta en Docker Hub y repositorio de imagen

Docker Hub almacena las imágenes del contenedor. El workflow de GitHub Actions construye y sube la imagen ahí; el servidor la descarga desde ahí.

hub.docker.com 
# 1. Crear cuenta en hub.docker.com

# 2. Crear repositorio público (gratis):
#    hub.docker.com → Repositories → Create → Nombre: sena-backend

# 3. Hacer login desde la terminal (para pruebas locales)
docker login -u tu-usuario-dockerhub

# 4. Construir y etiquetar la imagen con tu usuario de Docker Hub
docker build -t tu-usuario-dockerhub/sena-backend:latest .

# 5. Subir la imagen a Docker Hub
docker push tu-usuario-dockerhub/sena-backend:latest

# Verificar que está en Docker Hub:
# hub.docker.com/r/tu-usuario-dockerhub/sena-backend

Configurar GitHub Secrets — credenciales seguras

Los Secrets de GitHub son variables de entorno cifradas que solo el workflow puede leer. Nunca aparecen en los logs ni en el código.

GitHub → Settings → Secrets 
# En tu repositorio de GitHub:
# Settings → Secrets and variables → Actions → New repository secret

# Agregar estos 5 secrets:

# DOCKERHUB_USERNAME   → tu usuario de Docker Hub
# DOCKERHUB_TOKEN      → token de Docker Hub (no la contraseña)
#   Obtenerlo en: hub.docker.com → Account Settings → Security → New Access Token

# SSH_HOST             → IP pública de tu servidor VPS
# SSH_USER             → usuario SSH (generalmente "ubuntu")

ssh-keygen -t ed25519 -C "github-actions-deploy"

cat ~/.ssh/id_ed25519.pub      # ← agregar esto al servidor:
#                                  echo "..." >> ~/.ssh/authorized_keys
3

Workflow principal: CI/CD completo

El workflow tiene tres jobs encadenados: test (pytest), build-and-push (imagen Docker), y deploy (SSH al servidor). Si cualquier job falla, los siguientes no se ejecutan.

.github/workflows/deploy.yml 
name: CI/CD — Test, Build, Deploy

on:
  push:
    branches: [ main ]
  workflow_dispatch:   # permite lanzarlo manualmente desde GitHub UI

jobs:
  # ── Job 1: Ejecutar tests ──
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16-alpine
        env:
          POSTGRES_USER: test_user
          POSTGRES_PASSWORD: test_pass
          POSTGRES_DB: test_db
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-retries 5

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
          cache: 'pip'

      - name: Instalar dependencias
        run: pip install -r requirements.txt

      - name: Ejecutar pytest
        env:
          DB_USER: test_user
          DB_PASSWORD: test_pass
          DB_HOST: localhost
          DB_PORT: 5432
          DB_NAME: test_db
          JWT_SECRET_KEY: test-secret-key-solo-para-ci
          JWT_ALGORITHM: HS256
        run: pytest tests/ -v --tb=short

  # ── Job 2: Construir y subir imagen a Docker Hub ──
  build-and-push:
    needs: test   # solo si los tests pasan
    runs-on: ubuntu-latest
    outputs:
      image-tag: $${{ steps.meta.outputs.tags }}

    steps:
      - uses: actions/checkout@v4

      - name: Login a Docker Hub
        uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - name: Extraer metadatos (tag con SHA del commit)
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ${{ secrets.DOCKERHUB_USERNAME }}/sena-backend
          tags: |
            type=ref,event=branch
            type=sha,prefix=sha-

      - name: Construir y subir imagen
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          # Caché: reutiliza capas de la imagen anterior (builds más rápidos)
          cache-from: type=registry,ref=${{ secrets.DOCKERHUB_USERNAME }}/sena-backend:cache
          cache-to:   type=registry,ref=${{ secrets.DOCKERHUB_USERNAME }}/sena-backend:cache,mode=max

  # ── Job 3: Deploy en el servidor via SSH ──
  deploy:
    needs: build-and-push   # solo si la imagen se subió con éxito
    runs-on: ubuntu-latest

    steps:
      - name: Deploy via SSH
        uses: appleboy/ssh-action@v1
        with:
          host:     ${{ secrets.SSH_HOST }}
          username: ${{ secrets.SSH_USER }}
          key:      ${{ secrets.SSH_PRIVATE_KEY }}
          script: |
            cd /opt/sena-backend

            # Descargar la nueva imagen
            docker compose pull backend

            # Reiniciar solo el backend (sin downtime en db y nginx)
            docker compose up -d --no-deps backend

            # Limpiar imágenes antiguas (liberar espacio)
            docker image prune -f

            echo "✅ Deploy completado: $(date)"

Lleva el conocimiento más lejos

El pipeline falla si los tests necesitan conexión real a PostgreSQL. Configura pytest para usar una base de datos SQLite en memoria durante los tests del CI, sin modificar el código de producción. Usa una variable de entorno TESTING=true y override el DATABASE_URL en database.py.

📂 Ver solución del reto

▼

1. Modificar database.py para detectar el modo test

app/database.py 
import os
from dotenv import load_dotenv
from sqlalchemy.ext.asyncio import (
    create_async_engine, AsyncSession, async_sessionmaker
)
from sqlalchemy.orm import declarative_base

load_dotenv()

# Si TESTING=true, usar SQLite en memoria (sin PostgreSQL)
if os.getenv("TESTING") == "true":
    DATABASE_URL = "sqlite+aiosqlite:///./test.db"
else:
    DATABASE_URL = (
        f"postgresql+asyncpg://{os.getenv('DB_USER')}:{os.getenv('DB_PASSWORD')}"
        f"@{os.getenv('DB_HOST')}:{os.getenv('DB_PORT')}/{os.getenv('DB_NAME')}"
    )

engine = create_async_engine(
    DATABASE_URL,
    echo=False,
    # SQLite necesita este parámetro en modo async
    connect_args={"check_same_thread": False}
    if "sqlite" in DATABASE_URL else {}
)
AsyncSessionLocal = async_sessionmaker(
    bind=engine, class_=AsyncSession, expire_on_commit=False
)
Base = declarative_base()

async def get_db():
    async with AsyncSessionLocal() as session:
        yield session

2. Instalar aiosqlite como dependencia de test

requirements.txt 
# Agregar al requirements.txt:
aiosqlite   # driver async para SQLite (solo tests)

# O como dependencia separada en requirements-dev.txt:
# aiosqlite
# pytest
# httpx
# pytest-asyncio

3. Actualizar el job de test en el workflow (sin PostgreSQL)

    runs-on: ubuntu-latest
    # Sin "services: postgres:" — ya no lo necesitamos

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
          cache: 'pip'

      - name: Instalar dependencias
        run: pip install -r requirements.txt && pip install aiosqlite

      - name: Ejecutar pytest con SQLite
        env:
          TESTING: "true"            # ← activa SQLite en database.py
          JWT_SECRET_KEY: test-key
          JWT_ALGORITHM: HS256
          ACCESS_TOKEN_EXPIRE_MINUTES: "30"
        run: pytest tests/ -v --tb=short
# Ahora los tests corren sin PostgreSQL: más rápidos y sin dependencias externas
