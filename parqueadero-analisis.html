1 Introducción
Propósito, alcance y contexto del proyecto
🎯 1.1 Propósito

Este documento especifica los requisitos funcionales y no funcionales del sistema de gestión para el Parqueadero El Poblado, ubicado en el sector El Poblado de Medellín, Colombia. Está dirigido al equipo de desarrollo (aprendices ADSO ficha 3387459), al cliente (dueño del parqueadero) y al instructor como Product Owner.

El documento sigue el estándar IEEE 830-1998 (Recommended Practice for Software Requirements Specifications) y sirve como referente técnico para las fases posteriores de diseño, desarrollo y pruebas.

📐 1.2 Alcance

El sistema ParkControl es una aplicación web que gestionará el registro de ingreso y salida de vehículos (carros y motos), el cálculo automático de cobros por tiempo de estadía, la gestión de clientes con mensualidad y la generación de reportes diarios de recaudo.

⚠️
Fuera del alcance v1.0: pagos electrónicos, reconocimiento automático de placas (ANPR), integración con facturación DIAN, gestión de múltiples sedes, reservas de cupo en línea.

A partir de esta declaración inicial, el proceso de elicitación de requisitos (sesión de preguntas al cliente) reveló las siguientes reglas de negocio:

Pregunta del analistaRespuesta del cliente
¿Solo carros o también motos?Carros y motos, con tarifas distintas: carro $3.000/h, moto $1.500/h.
¿Se cobra por hora exacta o fracción?Por hora iniciada: toda fracción se paga como hora completa.
¿Hay tiempo de gracia?Sí, si sale en 10 minutos o menos, no se cobra.
¿Qué pasa si pierde el tiquete?Se cobra la tarifa máxima del día: $30.000.
¿Existen clientes con mensualidad?Sí, si la mensualidad está vigente salen sin cobro.
¿Cuál es la capacidad del parqueadero?50 puestos; si está lleno, no se permite el ingreso.
¿Qué reporte necesita al final del día?Total recaudado y número de vehículos atendidos.

3 Requisitos específicos
Requisitos funcionales y no funcionales del sistema ParkControl
✅ 3.1 Requisitos funcionales
IDRequisitoOrigen (cliente)
RF-01El sistema debe permitir al cajero registrar el ingreso de un vehículo capturando: placa, tipo (carro/moto) y hora de entrada, generando un tiquete digital.«registro la placa y la hora»
RF-02El sistema debe validar la disponibilidad de cupo (capacidad máxima: 50 puestos) antes de permitir el ingreso. Si el parqueadero está lleno, debe mostrar el mensaje «Parqueadero lleno — No hay cupo disponible».«hay 50 puestos»
RF-03El sistema debe permitir al cajero registrar la salida de un vehículo y calcular automáticamente el valor a cobrar según el tiempo transcurrido y la tarifa del tipo de vehículo (carro: $3.000/h, moto: $1.500/h).«cuando sale, cobro según el tiempo»
RF-04El sistema debe cobrar por hora iniciada: toda fracción de hora se cobra como hora completa (redondeo hacia arriba con ceil).«la fracción se paga completa»
RF-05El sistema debe aplicar un tiempo de gracia de 10 minutos: si el vehículo sale en 10 minutos o menos desde su ingreso, el valor a cobrar es $0.«si sale rapidito no le cobro»
RF-06El sistema debe permitir al cajero marcar un tiquete como «perdido», aplicando automáticamente la tarifa máxima del día ($30.000 COP) independientemente del tiempo real.«si pierde el tiquete, tarifa plena»
RF-07El sistema debe identificar vehículos con mensualidad vigente por su placa y permitir su salida sin cobro por tiempo. Si la mensualidad está vencida, se cobra normalmente.«tengo clientes de mensualidad»
RF-08El sistema debe generar un reporte de cierre diario que muestre: total recaudado ($), número de vehículos atendidos, desglose por tipo (carros/motos) y número de tiquetes perdidos.«quiero saber cuánto vendo al día»
RF-09El sistema debe permitir al cajero consultar un vehículo dentro del parqueadero por su placa, mostrando hora de entrada, tiempo transcurrido y valor acumulado en tiempo real.(descubierto al prototipar)
🔧 3.2 Requisitos no funcionales
IDCategoríaRequisitoMétrica de verificación
RNF-01UsabilidadEl registro de salida debe completarse en pocos pasos para que el cajero atienda la fila con agilidad.≤ 3 clics desde la búsqueda por placa hasta la confirmación del cobro.
RNF-02MantenibilidadLas tarifas por tipo de vehículo, el tiempo de gracia y la tarifa máxima deben ser parametrizables sin modificar el código fuente.Valores almacenados en tabla de configuración de la base de datos.
RNF-03TrazabilidadToda transacción de cobro debe quedar registrada con datos completos para auditoría.Log con: fecha, hora, placa, cajero, monto, tipo de cobro (normal/gracia/perdido/mensual).
📝
Diferencia clave: los requisitos funcionales describen QUÉ hace el sistema (registrar, calcular, cobrar); los no funcionales describen CÓMO debe ser el sistema (rápido, parametrizable, auditable).

5 Historias de usuario
Funcionalidades desde la perspectiva del usuario con criterios de aceptación BDD
📝
Como cajero, quiero registrar el ingreso de un vehículo capturando su placa y tipo, para tener control de los vehículos dentro del parqueadero.

Criterios de aceptación:

✅
CA-01.1: DADO QUE el parqueadero tiene cupo disponible, CUANDO el cajero registra placa «ABC123» tipo «carro», ENTONCES el sistema genera un tiquete con hora de entrada y muestra cupo restante.
✅
CA-01.2: DADO QUE el parqueadero tiene 50 vehículos (lleno), CUANDO el cajero intenta registrar una entrada, ENTONCES el sistema muestra «Parqueadero lleno» y no permite el registro.
✅
CA-01.3: DADO QUE la placa «ABC123» ya tiene un tiquete activo, CUANDO el cajero intenta registrar esa misma placa, ENTONCES el sistema muestra «Este vehículo ya se encuentra dentro del parqueadero».

RF trazados: RF-01, RF-02 · CU: CU-01

📝
Como cajero, quiero registrar la salida de un vehículo y que el sistema calcule automáticamente el valor a cobrar, para cobrarle correctamente al cliente y liberar el cupo.

Criterios de aceptación:

✅
CA-02.1 (Cobro normal): DADO QUE un carro ingresó hace 2 horas y 10 minutos, CUANDO el cajero registra la salida, ENTONCES el sistema cobra 3 horas × $3.000 = $9.000.
✅
CA-02.2 (Moto): DADO QUE una moto ingresó hace 1 hora y 45 minutos, CUANDO el cajero registra la salida, ENTONCES el sistema cobra 2 horas × $1.500 = $3.000.
✅
CA-02.3: DADO QUE el cobro se confirma, CUANDO el sistema registra la salida, ENTONCES el cupo disponible aumenta en 1 y la transacción queda registrada para el reporte diario.

RF trazados: RF-03, RF-04 · CU: CU-02

📝
Como cajero, quiero que el sistema reconozca automáticamente cuando un vehículo sale dentro del tiempo de gracia, para no cobrarle al cliente.

Criterios de aceptación:

✅
CA-03.1: DADO QUE un vehículo ingresó hace 7 minutos, CUANDO el cajero registra la salida, ENTONCES el valor es $0 y se muestra «Tiempo de gracia — Sin cobro».
✅
CA-03.2: DADO QUE un vehículo ingresó hace exactamente 10 minutos, CUANDO el cajero registra la salida, ENTONCES el valor es $0 (10 min está dentro del límite).
✅
CA-03.3: DADO QUE un vehículo ingresó hace 11 minutos, CUANDO el cajero registra la salida, ENTONCES se cobra 1 hora completa según la tarifa del tipo.

RF trazados: RF-05 · CU: CU-02 (flujo alterno a)

📝
Como cajero, quiero poder marcar un tiquete como perdido para aplicar la tarifa máxima del día y no dejar salir el vehículo gratis.

Criterios de aceptación:

✅
CA-04.1: DADO QUE un cliente dice que perdió su tiquete, CUANDO el cajero marca «Tiquete perdido» en el sistema, ENTONCES el valor a cobrar es $30.000 independientemente del tiempo real.
✅
CA-04.2: DADO QUE se registra un tiquete perdido, CUANDO se genera el reporte diario, ENTONCES la transacción aparece marcada como «tiquete perdido» en el desglose.

RF trazados: RF-06 · CU: CU-02 (flujo alterno b)

📝
Como cajero, quiero que el sistema identifique automáticamente si un vehículo tiene mensualidad vigente, para dejarlo salir sin cobro.

Criterios de aceptación:

✅
CA-05.1: DADO QUE la placa «XYZ789» tiene mensualidad vigente hasta el 30 de septiembre, CUANDO el cajero registra la salida el 15 de septiembre, ENTONCES el valor es $0 y se muestra Cliente mensual.
✅
CA-05.2: DADO QUE la placa «XYZ789» tenía mensualidad hasta el 31 de agosto (vencida), CUANDO el cajero registra la salida el 5 de septiembre, ENTONCES se cobra normalmente por tiempo y se muestra Mensualidad vencida.

RF trazados: RF-07 · CU: CU-02 (flujo alterno c), CU-06

📝
Como administrador, quiero generar un reporte de cierre diario con el total recaudado y los vehículos atendidos, para entregarle cuentas al dueño.

Criterios de aceptación:

✅
CA-06.1: DADO QUE se atendieron 35 vehículos hoy con un total de $120.000, CUANDO el administrador genera el reporte, ENTONCES el sistema muestra: Total recaudado: $120.000, Vehículos: 35, Carros: 20, Motos: 15, Tiquetes perdidos: 2.
✅
CA-06.2: DADO QUE no hay transacciones en la fecha seleccionada, CUANDO el administrador genera el reporte, ENTONCES el sistema muestra «No hay transacciones registradas para esta fecha».

RF trazados: RF-08 · CU: CU-04
